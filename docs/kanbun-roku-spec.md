## 1. 目的

Claudeとの会話ログを、原本のままDBに保存する。そこへリンクした、漢文調のダイアリーを作る。後から見返すとき、日記から原本へ辿れる。後日の考察は注釈の層として積み重ねる。

## 2. 原則

1. 原本（`messages`）は追記のみ。更新・削除をしない。
2. ダイアリーは原本からの派生物。いつでも原本から作り直せる。
3. ダイアリーの各記述は、根拠となる原本の発言にリンクする。
4. 注釈（`annotations`）は後日の考察を足す層。原本には触れない。
5. このリポジトリは公開。実データはコミットしない。テストはダミーデータだけで書く。
6. 会話ログは機微な個人情報。外部に送信しない（LLMはローカルのOllama）。

## 5. 取り込み（実装済み）

- 入力：claude.ai のエクスポート `conversations.json`（約165MB。392会話、うち発言0件が7会話、発言は22,852件）。

## 6. 区切り（座）の規則（実装済み）

### 基本

- 区切りは、1つの会話の中で閉じる（会話をまたがない）。
- 境界の日時は、2026-10-30 日本時間 0:00（2026-10-29T15:00:00Z）。境界をまたぐ区切りは分けない。切り替えは発言ごとの時刻で行う。
- 境界より前：6時間以上の間隔があいたところで区切る（`gap`）。終了の合図も再開の合図も効かない。
- 境界以降：合図の規則を適用する。

### 終了の合図

- 対象は人間（user）の発言。40文字以下で、全体が一致したときだけ。空白・句点・感嘆符の差は無視する。
- 集合（`END_PHRASES`。定数で、足せる）：こちらからは以上です / 中断します / おやすみなさい / さようなら / いってきます
- 合図の発言と、直後から次のuser発言までのassistantの返答を、閉じる側の区切りに含める（`end_reason = end_phrase`）。
- assistantの発言は合図にならない。
- 合図のあとに「再開します」以外の発言が来たら、新しい区切りを始める（`start_reason = after_end`）。

### 再開の合図

- 人間の発言が「再開します」と全体一致したら、新しい区切りの最初の発言にする（`start_reason = resume_phrase`、`resumed = true`）。
- 直前の区切りが開いたままなら、暗黙に閉じる（`end_reason = implicit`）。
- 同じ会話の直前の区切りを `continued_from` で結ぶ。別の会話で「再開します」と言った場合は、`resumed = true` かつ `continued_from = NULL`。
- 過去分に「再開します」は全期間で1件。過去分には適用しない。

### 開いた区切り（open）

- 合図がなく、最後の発言から6時間未満なら `open`。
- 合図のuser発言で終わり、返答がなく6時間未満なら `open`（返答待ち）。返答が入れば閉じる。
- 最後の発言から6時間以上たっていれば、返答がなくても閉じる（合図なしは `gap`、合図ありは `end_phrase`）。取り込み時刻との比較。
- 閉じた区切りは更新しない（注釈やタグが結びつくため）。`open` の区切りだけ、次の取り込みで先頭の発言から計算し直す。
- 日記は `open` の区切りには作らない。

### 日付

- 区切りの日付は、開始時刻の日本時間の暦日。
- 0時をまたいで続いた分は、表示のときに24時・25時と出す（25時制）。
- 午前1時に「再開します」と言って始めた区切りは、翌日の記録になる。

## 7. ダイアリーの生成（第1段階は実装済み・全825座を生成済み）

### 全体

- 1つの座から、1件のダイアリーを作る。
- 2段構成：1段目「曽良モード」（事実を簡潔に記録。原本へのリンク付き）→ 2段目「芭蕉モード」（紀行文として文章化。後回し）。
- 曽良モードの材料づくりは、さらに2つの呼び出しに分ける（A：人間の発言のみ、B：Claude の発言のみ。「A/Bの2段階方式」）。試走の結果、第1段階は A のみで進め、B は第2段階に先送りする（「決定：第1段階はAのみ」）。
- 生成はSolid Queueのジョブで、1件ずつ流す。日付や座を指定して作り直せる。
- 実装の状況：入力の前処理、A の生成（入力づくり、`OllamaClient`、`NoteParser`、`Generator`、引用の検証、機械後処理、`Assembler`、`GenerateDiaryJob`）、運用の rake（`diary:dry_run`、`diary:enqueue`、`diary:report`、`diary:retry_failed`、`diary:show`、`diary:reassemble`）は実装済み。A の本番の生成は、全825座で完了した（次の「全825座の実走結果」）。

### 入力の前処理

実装は `SegmentChunker`（DBに触れない純粋な関数）。

- 素材は `body` の本文だけ。`thinking` やツールの出力は使わない。
- user の発言は全文。assistant の発言は先頭N文字（`ASSISTANT_HEAD_CHARS`、初期値600）に切り詰め、切った箇所に「…（以下略）」を付ける。
- コードブロック（閉じていないものも）と、連続して300文字を超える引用行は、「（省略）」に置き換える（user・assistant とも）。
- paste_text（端末出力など）は、先頭5行と末尾5行だけ残し、間を「（貼付のため N 行省略）」にする（`PASTE_HEAD_LINES`、`PASTE_TAIL_LINES`）。
- 本文が空の user 発言には、入力でだけ使う印を入れる。image があれば「（画像）」、document があれば「（文書）」（両方なら続けて）、手がかりがなければ「（添付・本文なし）」。印は `body` に書き込まない（`messages` は不変）。
- Claude の文の貼り付けは、一致した部分だけを「（Claude文の貼り付け）」に置き換える（「貼り付けの出所照合」）。
- 1つの発言が単独で上限を超えるときは、先頭と末尾を残して、間を「（中略）」にする。人間の発言ブロックと流れの両方に載る発言（`flow: true`）は、同じ文が2回入るので、1回あたりの上限を半分にする。A の入力（`flow: false`）では、1回しか入らないので、半分にしない。
- `human_block: true` のとき、塊の先頭に「人間の発言」ブロック（user のうち utterance と paste_media の印だけを、日本時間の時刻つきで全件。paste_text は入れない）を置き、続けて「流れ」（時刻順。user は全文・貼付は先頭と末尾の数行、assistant は先頭600文字。ラベルは【人間】/【Claude】）を置く。座が日付をまたぐときは、時刻に月日を付ける。A の入力に使うのは、このブロックだけ。

### 貼り付けの出所照合（ClaudePasteDetector）

人間の発言が、Claude の文の貼り付けかを判定する。DBに触れない純粋なクラス。assistant の本文は初期化のときに渡す。

- 判定（連続一致）：発言と、assistant の本文のどれかとの、連続した一致が50字以上（`MIN_CHARS`）。正規化は NFKC のあと、空白・句読点・記号を除く。発言全体に占める割合は問わない（一致した部分だけを置き換えるので、残りは使える）。
- 照合の対象は、その発言より前の時刻の assistant メッセージだけ（`before:`、同時刻と後のものは使わない）。
- 判定（行規則、規則の版 2026-11-02.4）：発言の各行（正規化後）が、同じ会話の先行する assistant の発言に完全に含まれ、20字以上（`LINE_MIN_CHARS`）で、先行する user 発言に同じ行がなく、発言全体がその行でない場合に、その行を貼り付けの印にする。発言の空でない行の全部が該当する発言は印にしない。従来の50字以上の連続一致は従来どおり。
  - 閾値を20字にした根拠：15〜19字では、assistant の複数の発言に含まれる行が多く、人間の短文が混ざる。測定では、20字の規則の影響は98座（約12%）。
  - 事例の経緯：短い貼り付け（24字）が連続一致の50字に届かず見逃され、Claude の文が人間の考えとして引用された。
- 置き換えの単位は、一致した部分（スパン）。一致した部分だけを「（Claude文の貼り付け）」に置き換え、一致しない部分は元のまま残す。離れた複数の一致は別々に、すぐ隣り合う一致は1つにまとめる。範囲の直後に続く句読点・記号は一致に含める（空白・改行は含めない）。
- 位置の対応表：正規化後の1文字ごとに、元の文のどのクラスタ（文字位置の範囲）から来たかを持つ（`normalize_with_map`）。NFKC は文字の並びで結果が変わる（半角カナ＋濁点など）ので、書記素クラスタごとに行い、1文字が複数に展開されても元の1クラスタに対応づける。
- 置き換えたあとの残りにシェルのプロンプト行・端末ノイズ（上の `prompt_lines?`）があれば、その発言は paste_text として扱う（人間の発言ブロックに入れず、貼付の省略を適用）。
- 対象は utterance だけ。assistant の発言、paste_text、paste_media には使わない。
- 全会話の結果（2026-11-02、連続一致のみ、行規則を入れる前。直前までの Claude 発言のみ、割合条件なし）：人間の utterance（本文あり）5,860件のうち301件（5.14%）が該当。該当のある座は171座（発言のある805座の21.2%）。残る部分の長さ（正規化後）は、0字41 / 1〜9字3 / 10〜29字47 / 30〜99字116 / 100字以上94。残りにプロンプト行などがあり paste_text へ移る件数は106。
- 変更の経過：全時刻の assistant と照合し、「一致が発言の50%以上」を条件にしていたときは192件（3.28%）。割合条件を外すと324件、直前までに限ると301件。
- 実測：索引に約720万字ぶんの50字の窓を持つので、ピークのメモリは約890MB、実行は約12秒。
- 確認用に、`segments:paste_origin_report` に `SEGMENT=id AT=HH:MM SHOW=1` を付けると、その発言の置き換え後の本文（先頭200字）と一致の長さ・割合を、端末にだけ出す。

#### Q:/A: 形式の扱い

- 人間の発言が「Q:」「A:」の形式で書かれているとき、「A:」の行は、人間が選んだ決定として「決定」に入れる（A の指示文に明記。引用は「A:」の行から写す。「人間の考え」には書かない）。
- 「A:」の行は、行頭の `A:` または `A：`（箇条書き記号は許す）。NFKC のあとで見る。
- 全会話で、「A:」行を含む user 発言は63件（utterance 62、paste_text 1）、44座。うち60件は同じ発言に「Q:」行もある。
- 機械的な見落とし検査（決定語の数）は、「A:」行を別の数として数える。

#### 決定語の一覧（見落とし検査用）

- 正規表現：`に(する|します|しました|しましょう)|で(いく|いきます|いきましょう)|とします|決めた|決めました|決定|進めます|よしとします|優先します|承認します|採用`
- 「お願いします」「ください」は入れない（依頼の言い回しのため）。「決定」は広い語で、決定でない使い方も数える。
- 検査：決定語（または「A:」行）を含む人間の発言があるのに、A の「決定」が0の座を列挙する。
- 広い目印（`Coverage::BROAD_DECISION_RE`）：上の一覧に「にしたい」「でいい」「それでお願い」「見送り」「方針」などを足した、検査専用の一覧。`diary:report` は狭い・広いの2つの数を出す。再分類（c）には使わず、`DECISION_RE` は変えない（生成結果が変わらないので `Rules::VERSION` は上げない）。
- 目視用：`bin/rails diary:missed_ids` が、決定語ありで決定0の座と、広い目印だけが反応する決定0の座のid（各10座。`N=` で変更）だけを出す。本文は出さない。

### A/Bの2段階方式

1つの座を、人間の発言と Claude の発言に分けて、それぞれ別の呼び出しで記録する。どちらの考えかが混ざる誤りを、入力の段階で防ぐため。

- **A（人間の記録）**：入力は人間の発言ブロックだけ（utterance と paste_media の印、時刻つき、時刻順）。Claude の発言は一切入れない。見出し（件数の上限）：
  - 人間の依頼・共有（5）：人間が Claude に何かを求めた（「〜してください」「〜を教えて」など）、または資料・結果を共有した。
  - 決定（5）：人間が選択肢から選んだ、提案を承認した、方針・行動を決めた（「〜にします」「〜でいきます」「〜とします」、Q:/A: の A:）。依頼は含めない。
  - 人間の考え（5）：人間が自分の見方・推測・感想・評価を述べた。事実の報告や依頼は含めない。
  - 未解決（3）：人間がまだ答えの出ていない疑問や課題として述べたもの。
- A の指示文の規則：入力にあることだけを書く。数字・固有名詞・URL・ハッシュは入力のまま写す。「（Claude文の貼り付け）」の印の内容は、依頼・決定・考えにしない。引用にも印を含めない。印の前後の人間の文だけを根拠にする。「（画像）」などの印だけの発言は、本文を「画像・文書を共有した」とし、引用は空にする。なければ空の配列でよい。件数を合わせるために書かない。同じ内容を複数の見出しに書かない。
- **B（Claude の記録）**：入力は Claude の発言（先頭600文字）と、A の出力の「人間の依頼・共有」の項目だけ（流れの手がかり。人間の考えは入れない）。見出しは「Claudeの提案・判断」（上限3）。試走の結論により、B は第1段階に含めない。
- 呼び出しは塊ごと。複数の塊の座は、A の結果を連結して後処理する（全825座で、有効な塊は825件。すべて1塊）。

### 出力形式（JSON schema）と引用の検証

- Ollama の `format`（JSON スキーマ）で構造を固定する。見出しは、項目の配列をもつキー。各項目は「本文」と「引用」の2つの文字列キー（A の見出しはすべて同じ形）。件数は `maxItems` で上限だけ決め、下限は設けない。これで、見出しの欠落や「- - 」のような形式崩れが起きない。試走の全呼び出し（A・B とも）で、JSON の崩れ・パース失敗・長さによる打ち切りは0件。`num_predict` は3000。

### 第3段階の案：共通知（案・未実装、2026-11-07に方針を決めた）

人間と Claude の発言を別々の層に分けず、**双方の意見・判断が一致したもの**を「共通知」として記録する。A（人間の記録）と B（Claude の記録）を足し合わせるのではなく、A の上に積む派生物にする。

  - 第2段階の B（Claude の提案・判断を独立に判定する案）とは別の層。B を作る場合も、共通知はその結果を材料にできる。

- **範囲を2段に分ける**

  - 合意：Claude の案に、人間が明示的に賛成・採用・選択した。
  - 修正つきの受け入れ：人間が案を一部変えて受け入れた。
  - 案が不明：人間の受け入れは読み取れるが、候補の発言に案が見当たらない（直前の発言が対象の提案とは限らないため）。
  - 不一致：人間が案を退けた、または別の方針を示した。
  - 日記に出すのは「合意」と「修正つきの受け入れ」だけ。他の区分は判定の記録として残すが、本文に出さない。人間が受け入れの言葉を返しただけでは、案を理解して賛成した保証にならない。偽の合意（Claude に合わせただけの受け入れ）の混入は、試作の主な確認項目にする。

- **入力**：決定項目の本文・引用と、リンク先の人間の発言、直前の assistant 発言（先頭 `ASSISTANT_HEAD_CHARS` 字。A/B 方式の B と同じ長さ）。1つの座の決定項目をまとめて1回の呼び出しにする。LLM はローカルの Ollama のみ。外部に送らない。
- **出力**：項目ごとに、共通知の本文（現代日本語、1文）、判定の区分、人間側の引用、assistant 側の引用。引用は、それぞれの発言の部分文字列であることを機械で検証する（A の `QuoteVerifier` と同じ考え方）。

- **置き場所（案）**
  - 新しいテーブル `common_notes`：`segment_id`（座。ダイアリーと同じく座単位）、`diary_entry_id`、`item_key`（元の決定項目。例「決定:2」）、`body`、`judgment`、`model`、`prompt_version`（共通知の指示文の版。`C-YYYY-MM-DD.n`）、`rule_version`（共通知を作ったときの後処理・検証の規則の版）、`input_digest`、`generated_at`。座ごとの作り直しは、同じ行の書き換え、または座単位の入れ替え。
  - 新しいテーブル `common_note_links`：`common_note_id`、`message_id`、`link_kind`（`human_source` / `assistant_source`）。
  - 注釈（`annotations`）は、`CommonNote` も対象にできる（多態）。注釈が付いた `common_notes` は削除できない（restrict）。
  - A の `diary_entries.note` には混ぜない。`reassemble`（A の組み立て直し）に巻き込まれないため。
  - 塊の記録は既存の `diary_chunks` に、`prompt_version` を `C-…` で区別して置く（一意キーに `prompt_version` が入っているため、新しい表は要らない）。
- **版**：共通知用の指示文の版（`C-YYYY-MM-DD.n`）を持つ。A と同じく、指示文・スキーマ・設定の指紋をテストで固定する。後処理や検証の規則の版（`common_notes.rule_version`）は、A の `Rules::VERSION` とは別にする（A を作り直しても共通知が巻き込まれない・その逆もないように、入力の `input_digest` に A の版を入れる）。

- **見込み（2026-11-07時点の実測）**：対象は、候補リンクのある決定項目 669件（395座）。座ごとに1回の呼び出しとして、`A-2026-11-06.1` の平均 32.9秒/塊で約3.6時間（395 × 32.9秒）。項目ごとに1回呼ぶ場合の上限の目安は、669 × 32.9秒 ≒ 約6.1時間。ペアの入力は A より小さい見込みなので、実際はこれより短い。

  3. 全座で塊のみ生成して比較し、採用を決める。
  4. `CLAUDE.md` に第3段階を足す。

### モデル

- 呼び出しは `Diary::OllamaClient`（Net::HTTP による自前のクライアント）。RubyLLM は使わない（`format` の JSON スキーマ、`think: false`、`seed`、モデルの digest、トークン数・所要時間の記録を、直接扱うため）。
- 接続先は環境変数（`OLLAMA_API_BASE`。例 `http://localhost:11434`）。コードには固定しない（公開リポジトリのため）。モデル名も環境変数（`DIARY_MODEL`、既定 `qwen3-14b-16k`）。
- 「メンタムさん」は、開発環境のローカルLLMの総称。メインは14b。
- 候補：`qwen3-14b-16k`、`qwen38-27b-q2k-waka`、`qwen3:30b-a3b`。短い座と長い座を1つずつ選び、同じ入力と指示で読み比べる。基準は、事実の正確さ、文体、所要時間。実際の試走（sora6〜sora9）は `qwen3-14b-16k` のみ。27b と30b の読み比べは、途中で打ち切った（「試走の結論」）。

### タグ

- 座とダイアリーに付ける。原本（`messages`）には付けない。
- 自動のタグは、ダイアリーを作り直すと入れ替わる。手動のタグは残る。
- 表記の揺れ（「連歌」と「れんが」など）は、正規化（辞書、全角半角の統一）で吸収する。新しいタグを「候補」として保留し、確認して採用する形も検討する。
- 検索：タグで一覧、複数タグの絞り込み、関連タグ。画面は、日記が作れてから。

## 8. 運用

### バックアップ（実装済み）

- `bin/backup-db`：`pg_dump` を gzip し、検証（`gzip -t`）してから配る。`.partial` で書いて、名前を直す。
- 保存先：外付けHDD（必須。書けなければERROR）と、外付けSSD（マウントされていれば）。それぞれ7世代を残す。
- NASには置かない（会話の全文を含むダンプを共有フォルダに置かないため）。
- launchd（LaunchAgent）で、毎日03:00。`ProgramArguments` は `["/bin/bash", "<スクリプトのパス>"]` の形にする。スクリプトを直接起動すると、外付けへの書き込みが `Operation not permitted` になった（理由は未調査）。
- `/bin/bash` にフルディスクアクセスが必要。
- スクリプトは内蔵ディスクに置いて、リポジトリ側の原本からコピーする。`plist` やスクリプトを変えたら、再コピーして再登録する。
- ログ：`log/backup.log`。復元は別名DBに戻して件数を確認する手順を確認済み。
- 手動で取るときは `launchctl kickstart -k gui/$(id -u)/com.kanbun-roku.backup`。

### ダイアリー生成の運用メモ

- `bin/jobs` は環境変数 `OLLAMA_API_BASE`（例 `http://localhost:11434`）が必須。未設定だと例外で止まる。
- コードを変えたあとは、`bin/jobs` を再起動する（古いコードを読み込んだままになるため）。
- 投入は `diary:enqueue`（`LIMIT=` 件数（既定100）、`SEGMENTS=` 座の指定、`APPLY=1` のときだけ投入）。規則（後処理・検証）だけを変えたときは、LLM を呼ぶ `diary:enqueue` ではなく `diary:reassemble` で再適用する。
- テスト：`ConversationSegmenter` のテストが時刻に依存していたので、`now` を固定した。

### Git

- 公開リポジトリ。コミットのメールアドレスは、このリポジトリだけ、GitHubのnoreplyアドレス。
- コミット前に、パスやホスト名の混入を `git grep --cached` で確認する。
- `data/`、`log/`、バックアップ（`*.sql.gz`）、`master.key`、`vendor/bundle` はGit管理外。

### 公開前のマスキング（未実施）

- 会話ログには、IPアドレス、ホスト名、ユーザー名、ホームパスなどが、端末出力の貼り付けなどの形で含まれる。公開前のマスキングは、**未実施の作業**。
- 実施するまでの運用：ログの実データや、そこから作った出力は、リポジトリにコミットしない。テストはダミーデータだけで書く。コミット前に `git grep --cached` で混入を確認する。
- クラウドのモデルにログを送る場合は、**マスキングを先に済ませることを前提**とする。現状は、LLM の呼び出しをローカルの Ollama に限っている（原則6）。
