## 1. 目的

Claudeとの会話ログを、原本のままDBに保存する。そこへリンクした、漢文調のダイアリーを作る。後から見返すとき、日記から原本へ辿れる。後日の考察は注釈の層として積み重ねる。

## 2. 原則

1. 原本（`messages`）は追記のみ。更新・削除をしない。
2. ダイアリーは原本からの派生物。いつでも原本から作り直せる。
3. ダイアリーの各記述は、根拠となる原本の発言にリンクする。
4. 注釈（`annotations`）は後日の考察を足す層。原本には触れない。
5. このリポジトリは公開。実データはコミットしない。テストはダミーデータだけで書く。
6. 会話ログは機微な個人情報。外部に送信しない（LLMはローカルのOllama）。

- モデル側で、保存済みの原本の更新と削除を拒否する。

## 5. 取り込み（実装済み）

- 既定は dry-run。`APPLY=1` を付けたときだけ書く。全体を1トランザクションで書き、再実行しても重複しない（冪等）。

## 6. 区切り（座）の規則（実装済み）

### 基本

- 区切りは、1つの会話の中で閉じる（会話をまたがない）。
- 境界の日時は、2026-10-30 日本時間 0:00（2026-10-29T15:00:00Z）。境界をまたぐ区切りは分けない。切り替えは発言ごとの時刻で行う。
- 境界より前：6時間以上の間隔があいたところで区切る（`gap`）。終了の合図も再開の合図も効かない。
- 境界以降：合図の規則を適用する。

### 終了の合図

- 対象は人間（user）の発言。40文字以下で、全体が一致したときだけ。空白・句点・感嘆符の差は無視する。
- 集合（`END_PHRASES`。定数で、足せる）：こちらからは以上です / 中断します / おやすみなさい / さようなら / いってきます
- 合図の発言と、直後から次のuser発言までのassistantの返答を、閉じる側の区切りに含める（`end_reason = end_phrase`）。
- assistantの発言は合図にならない。
- 合図のあとに「再開します」以外の発言が来たら、新しい区切りを始める（`start_reason = after_end`）。

### 再開の合図

- 人間の発言が「再開します」と全体一致したら、新しい区切りの最初の発言にする（`start_reason = resume_phrase`、`resumed = true`）。
- 直前の区切りが開いたままなら、暗黙に閉じる（`end_reason = implicit`）。
- 同じ会話の直前の区切りを `continued_from` で結ぶ。別の会話で「再開します」と言った場合は、`resumed = true` かつ `continued_from = NULL`。
- 過去分に「再開します」は全期間で1件。過去分には適用しない。

### 開いた区切り（open）

- 合図がなく、最後の発言から6時間未満なら `open`。
- 合図のuser発言で終わり、返答がなく6時間未満なら `open`（返答待ち）。返答が入れば閉じる。
- 最後の発言から6時間以上たっていれば、返答がなくても閉じる（合図なしは `gap`、合図ありは `end_phrase`）。取り込み時刻との比較。
- 閉じた区切りは更新しない（注釈やタグが結びつくため）。`open` の区切りだけ、次の取り込みで先頭の発言から計算し直す。
- 日記は `open` の区切りには作らない。

### 日付

- 区切りの日付は、開始時刻の日本時間の暦日。
- 0時をまたいで続いた分は、表示のときに24時・25時と出す（25時制）。
- 午前1時に「再開します」と言って始めた区切りは、翌日の記録になる。

## 7. ダイアリーの生成（第1段階の方式は確定、生成は未実装）

### 全体

- 1つの座から、1件のダイアリーを作る。
- 2段構成：1段目「曽良モード」（事実を簡潔に記録。原本へのリンク付き）→ 2段目「芭蕉モード」（紀行文として文章化。後回し）。
- 曽良モードの材料づくりは、さらに2つの呼び出しに分ける（A：人間の発言のみ、B：Claude の発言のみ。「A/Bの2段階方式」）。試走の結果、第1段階は A のみで進め、B は第2段階に先送りする（「決定：第1段階はAのみ」）。
- 生成はSolid Queueのジョブで、1件ずつ流す。日付や座を指定して作り直せる。
- 実装の状況：入力の前処理（分類、貼り付けの照合、塊分け）は実装済み。生成のジョブ、結果の保存、機械後処理のリポジトリへの実装は未着手。

### 曽良モードの出力形式（旧案。A/Bの方式に置き換え）

試走の前の案。今の出力形式は「出力形式（JSON schema）と引用の検証」を正とする。

| 項目 | 内容 |
|---|---|
| 事実 | 何が行われたか。数字や固有名詞は原文と一致させる。 |
| 決定 | その座で決まったこと。 |
| 未解決 | 残った課題や保留。 |
| 考察 | 原文で語られたものに限る。由来（userかassistantか）を明示する。 |
| タグ | 3〜6個の名詞。 |

- リンクの粒度は、最初は座全体に1つ。モデルの出来を見てから、文ごとのリンクに進む。
- 文体は簡潔な漢字主体の記録体を目標にする。漢文の白文は下書きとして扱い、原文（現代語）と書き下し文を併記する。直した差分は注釈の層に残し、文体の見本として使う。見本には『奥の細道』（著作権切れ）を使える。

### 入力の前処理

実装は `SegmentChunker`（DBに触れない純粋な関数）。

- 素材は `body` の本文だけ。`thinking` やツールの出力は使わない。
- user の発言は全文。assistant の発言は先頭N文字（`ASSISTANT_HEAD_CHARS`、初期値600）に切り詰め、切った箇所に「…（以下略）」を付ける。
- コードブロック（閉じていないものも）と、連続して300文字を超える引用行は、「（省略）」に置き換える（user・assistant とも）。
- paste_text（端末出力など）は、先頭5行と末尾5行だけ残し、間を「（貼付のため N 行省略）」にする（`PASTE_HEAD_LINES`、`PASTE_TAIL_LINES`）。
- 本文が空の user 発言には、入力でだけ使う印を入れる。image があれば「（画像）」、document があれば「（文書）」（両方なら続けて）、手がかりがなければ「（添付・本文なし）」。印は `body` に書き込まない（`messages` は不変）。
- Claude の文の貼り付けは、一致した部分だけを「（Claude文の貼り付け）」に置き換える（「貼り付けの出所照合」）。
- 1つの発言が単独で上限を超えるときは、先頭と末尾を残して、間を「（中略）」にする。人間の発言ブロックにも載る発言は、同じ文が2回入るので、1回あたりの上限を半分にする。
- `human_block: true` のとき、塊の先頭に「人間の発言」ブロック（user のうち utterance と paste_media の印だけを、日本時間の時刻つきで全件。paste_text は入れない）を置き、続けて「流れ」（時刻順。user は全文・貼付は先頭と末尾の数行、assistant は先頭600文字。ラベルは【人間】/【Claude】）を置く。座が日付をまたぐときは、時刻に月日を付ける。A の入力に使うのは、このブロックだけ。
- 上限を超える座は、発言の境界で塊に分ける。塊ごとに A を呼び、結果は機械で連結して後処理する（LLM による統合は行わない。「機械後処理」）。

### 発言の分類（MessageClassifier）

DBに触れない純粋な関数 `classify(role:, body:, raw:)`。結果は保存しない。

| 分類 | 条件 |
|---|---|
| paste_text | user の発言で、端末出力などの貼り付けと見られるもの。（a）シェルのプロンプト行を含み、空でない行が3行以上（`SHELL_PROMPT_MIN_LINES`）、または（b）長い複数行（空でない行が20行以上（`PASTE_MIN_LINES`）かつ1,200文字以上（`PASTE_MIN_CHARS`））。 |
| paste_media | user の発言で、本文が空で、raw に image / document の手がかりがあるもの。 |
| utterance | それ以外。assistant の発言はすべてここ。 |

- プロンプト行（`SHELL_PROMPT`）：行頭が「user@host dir % cmd」「$ cmd」「% cmd」「❯ cmd」「➜ dir」の形の行。venv の「(env) 」は許す。
- media の手がかり（raw）：`content` のブロック（image / document）、`files`（拡張子が画像なら image、それ以外と拡張子なしは document）、`attachments`（document）。content のブロックは files の一部にしか付かない（画像拡張子の files のうちブロックが付くのは約17%）ので、files も見ないと画像の多くを取りこぼす。
- 本文のある発言は、添付があっても paste_media にしない。
- 貼り付けの置き換え後の残りに端末出力の行があるかの判定（`prompt_lines?`）は、行数の下限を設けず、プロンプトだけの行（コマンドなし）、「~ $」、`Password:`、行頭の「NN%」または「NN%」のあとに進捗バーの記号が続く行も、端末出力とみなす。文末の「50%」やメールアドレスだけの行は拾わない。
- 全833座の分類結果（2026-11-01、貼り付けの出所照合を入れる前）：role=user の発言11,413件のうち、paste_text 3,477 / paste_media 2,070 / utterance 5,866。paste_text の大半（約2,600件）はシェルのプロンプト行で拾ったもので、長い複数行だけで拾ったのは約90件。
- 本文が空の user 発言2,076件の内訳（content・files・attachments を見る）：image 1,598 / document 459 / 両方13 / どちらもない6。content のブロックだけで見ると、image 144 / document 72 / どちらもない1,860。
- utterance の1件あたり文字数（最小 / 中央値 / 最大）：user 0 / 36 / 3,263、assistant 0 / 459 / 17,342。

### 座の型（SegmentTyper）

- 貼り付け（paste_text と paste_media）の比率で、座を work / talk に分ける。比率は、座の中の user 発言の数に対する貼り付けの数（assistant の発言は数えない）。閾値 `WORK_PASTE_RATIO` = 0.3 以上が work、未満が talk。user の発言がない座は talk。
- 全833座：work 323 / talk 510。貼り付けの比率（座ごと）は、p25 = 0、p50 = 0、p75 = 0.5、p90 = 0.71、最大 1.0。
- 型は表示や絞り込みのための派生情報で、生成の分岐にはまだ使っていない。

### 文脈の見積もりとチャンカーの統計

- モデル `qwen3-14b-16k`、`num_ctx = 16384` を明示する（入力が超えると黙って切り詰められることがあるため）。
- 思考（thinking）は切る。Ollama の `think: false` が、試走の全呼び出しで効いた（thinking は0文字）。
- 入力の上限（`INPUT_LIMIT`）：16,384 − 指示文の見積もり（仮の指示文で257） − テンプレート100 − 出力2,000 を、100単位で切り捨てて14,000トークン。A・B の指示文は、仮の指示文より長いので、見直しが要る。
- トークン数の見積もり（`SegmentChunker.estimate_tokens`、文字種別の式）：漢字×1.4 ＋ その他の非ASCII×0.6 ＋ ASCII×0.4、全体に安全係数1.15を掛ける。30件の実測（`prompt_eval_count`）で較正した。係数1.0では30件中1件が最大6.5%の過小。1.15で全件が実測以上（最小で約1.08倍）。実際の塊6個では、見積もりが実測の約1.3〜1.4倍で、過小はなかった。絵文字などは未較正。
- 文字数とトークン数の比（30件の測定、本文のみ）：最小1.27 / 下位10%で1.51 / 中央値1.70 / 75%で2.02 / 最大5.28。ASCII はコードやURLの量で実測が0.2〜0.5と振れる。
- 塊の数（全833座、人間の発言ブロックあり）：貼り付けの置き換えなしで946塊（1塊747 / 2塊68 / 3塊11 / 4塊5 / 5塊2。2塊以上の座は86）。置き換え・paste_text への移動ありで942塊（1塊751 / 2塊64 / 3塊11 / 4塊5 / 5塊2。2塊以上の座は82）。
- 前処理によるトークン削減（見積もり、塊分けの初期の dry-run、全833座）：前処理前7,272,441 → assistant の切り詰めとコード・引用の省略で5,092,700（30.0%減）→ 貼付省略で4,211,112（前処理前から42.1%減。貼付省略だけで17.3%減）。
- 単独で上限を超える発言は、前処理前に1件、前処理後も1件（中略になる）。
- 報告用のタスク（読み取りのみ、本文は出さない）：`bin/rails segments:chunk_report`、`segments:classify_report`、`segments:paste_origin_report`。

### 貼り付けの出所照合（ClaudePasteDetector）

人間の発言が、Claude の文の貼り付けかを判定する。DBに触れない純粋なクラス。assistant の本文は初期化のときに渡す。

- 判定：発言と、assistant の本文のどれかとの、連続した一致が50字以上（`MIN_CHARS`）。正規化は NFKC のあと、空白・句読点・記号を除く。発言全体に占める割合は問わない（一致した部分だけを置き換えるので、残りは使える）。
- 照合の対象は、その発言より前の時刻の assistant メッセージだけ（`before:`、同時刻と後のものは使わない）。
- 置き換えの単位は、一致した部分（スパン）。一致した部分だけを「（Claude文の貼り付け）」に置き換え、一致しない部分は元のまま残す。離れた複数の一致は別々に、すぐ隣り合う一致は1つにまとめる。範囲の直後に続く句読点・記号は一致に含める（空白・改行は含めない）。
- 位置の対応表：正規化後の1文字ごとに、元の文のどのクラスタ（文字位置の範囲）から来たかを持つ（`normalize_with_map`）。NFKC は文字の並びで結果が変わる（半角カナ＋濁点など）ので、書記素クラスタごとに行い、1文字が複数に展開されても元の1クラスタに対応づける。
- 置き換えたあとの残りにシェルのプロンプト行・端末ノイズ（上の `prompt_lines?`）があれば、その発言は paste_text として扱う（人間の発言ブロックに入れず、貼付の省略を適用）。
- 対象は utterance だけ。assistant の発言、paste_text、paste_media には使わない。
- 全会話の結果（2026-11-02、直前までの Claude 発言のみ、割合条件なし）：人間の utterance（本文あり）5,860件のうち301件（5.14%）が該当。該当のある座は171座（発言のある805座の21.2%）。残る部分の長さ（正規化後）は、0字41 / 1〜9字3 / 10〜29字47 / 30〜99字116 / 100字以上94。残りにプロンプト行などがあり paste_text へ移る件数は106。
- 変更の経過：全時刻の assistant と照合し、「一致が発言の50%以上」を条件にしていたときは192件（3.28%）。割合条件を外すと324件、直前までに限ると301件。
- 実測：索引に約720万字ぶんの50字の窓を持つので、ピークのメモリは約890MB、実行は約12秒。
- 確認用に、`segments:paste_origin_report` に `SEGMENT=id AT=HH:MM SHOW=1` を付けると、その発言の置き換え後の本文（先頭200字）と一致の長さ・割合を、端末にだけ出す。

#### Q:/A: 形式の扱い

- 人間の発言が「Q:」「A:」の形式で書かれているとき、「A:」の行は、人間が選んだ決定として「決定」に入れる（A の指示文に明記。引用は「A:」の行から写す。「人間の考え」には書かない）。
- 「A:」の行は、行頭の `A:` または `A：`（箇条書き記号は許す）。NFKC のあとで見る。
- 全会話で、「A:」行を含む user 発言は63件（utterance 62、paste_text 1）、44座。うち60件は同じ発言に「Q:」行もある。
- 機械的な見落とし検査（決定語の数）は、「A:」行を別の数として数える。

#### 決定語の一覧（見落とし検査用）

- 正規表現：`に(する|します|しました|しましょう)|で(いく|いきます|いきましょう)|とします|決めた|決めました|決定|進めます|よしとします|優先します|承認します|採用`
- 「お願いします」「ください」は入れない（依頼の言い回しのため）。「決定」は広い語で、決定でない使い方も数える。
- 検査：決定語（または「A:」行）を含む人間の発言があるのに、A の「決定」が0の座を列挙する。

### A/Bの2段階方式

1つの座を、人間の発言と Claude の発言に分けて、それぞれ別の呼び出しで記録する。どちらの考えかが混ざる誤りを、入力の段階で防ぐため。

- **A（人間の記録）**：入力は人間の発言ブロックだけ（utterance と paste_media の印、時刻つき、時刻順）。Claude の発言は一切入れない。見出し（件数の上限）：
  - 人間の依頼・共有（5）：人間が Claude に何かを求めた（「〜してください」「〜を教えて」など）、または資料・結果を共有した。
  - 決定（5）：人間が選択肢から選んだ、提案を承認した、方針・行動を決めた（「〜にします」「〜でいきます」「〜とします」、Q:/A: の A:）。依頼は含めない。
  - 人間の考え（5）：人間が自分の見方・推測・感想・評価を述べた。事実の報告や依頼は含めない。
  - 未解決（3）：人間がまだ答えの出ていない疑問や課題として述べたもの。
- A の指示文の規則：入力にあることだけを書く。数字・固有名詞・URL・ハッシュは入力のまま写す。「（Claude文の貼り付け）」の印の内容は、依頼・決定・考えにしない。引用にも印を含めない。印の前後の人間の文だけを根拠にする。「（画像）」などの印だけの発言は、本文を「画像・文書を共有した」とし、引用は空にする。なければ空の配列でよい。件数を合わせるために書かない。同じ内容を複数の見出しに書かない。
- **B（Claude の記録）**：入力は Claude の発言（先頭600文字）と、A の出力の「人間の依頼・共有」の項目だけ（流れの手がかり。人間の考えは入れない）。見出しは「Claudeの提案・判断」（上限3）。試走の結論により、B は第1段階に含めない。
- 呼び出しは塊ごと。複数の塊の座は、A の結果を連結して後処理する。

### 出力形式（JSON schema）と引用の検証

- Ollama の `format`（JSON スキーマ）で構造を固定する。見出しは、項目の配列をもつキー。各項目は「本文」と「引用」の2つの文字列キー（A の見出しはすべて同じ形）。件数は `maxItems` で上限だけ決め、下限は設けない。これで、見出しの欠落や「- - 」のような形式崩れが起きない。試走の全呼び出し（A・B とも）で、JSON の崩れ・パース失敗・長さによる打ち切りは0件。`num_predict` は3000。
- 引用は「本文を直接裏づける発言の一部」。40文字以内で、言い換えずにそのまま写す。
- 引用の検証（機械）：引用と、対応する側の発言（A は人間の発言、B は Claude の発言）を、NFKC・空白・句読点・記号・括弧・アスタリスク・バッククォートを除いて比べる。
  - 合格：引用が対応する側の発言に含まれる。
  - 不合格：引用が空（引用なし）、対応する側にない（入力にない）、逆の発言者の発言にだけある、「（Claude文の貼り付け）」の印を含む。
  - 短い断片：正規化後10字未満で、文の途中から始まり文末で終わる引用は、不合格として数える（文全体が短い発言は断片としない）。
  - 免除：本文が「画像・文書を共有した」で引用が空の項目は、引用なしに数えない。
- 検証で見つかるのは、引用が入力にあるかまで。本文と引用の意味のずれ（誤読）は、機械では検出できない。

### 機械後処理

LLM を使わず、A の出力に当てる。

- 見出し間の重複除去：優先度は、決定 > 人間の考え > 未解決 > 人間の依頼・共有。本文の文字2-gramの Dice 係数が0.5以上の項目を重複とし、優先度の低い側を落とす。同じ見出しの中では落とさない。
- 塊の連結：複数の塊の座は、全塊の項目を連結してから、同じ規則で重複を落とす。
- 再分類ルール（c）：「決定」の引用が「ください」「お願いします」「ますか」で終わる項目は、「人間の依頼・共有」に移す。
- 検証（sora6の30区間、A の出力）：項目291件のうち29件を落として262件（落とした見出しは依頼・共有18、未解決11。決定と人間の考えは0）。複数の塊の8座を連結しても、塊ごとより追加で落ちた項目は0。（c）に当たる決定は30件中5件。このほか、本文と引用がほぼ同一（Dice 0.9以上）の項目が91件（引用ありの34.2%）、同じ引用が複数の項目で使われているものが23組・52項目。
- 状況：試走用スクリプトでの検証のみ。リポジトリには未実装。

### 試走の結論（sora6〜sora9）

条件：`qwen3-14b-16k`、`think: false`、温度0.2、`num_ctx` 16384、A・B とも塊ごと。対象は、層別に選んだ座（sora6：30区間）と、14区間（sora7〜sora9。前回の6区間に、見出しの確認用、貼り付けの確認用、「A:」行を含む座を足したもの）。

- **A は安定。調整は打ち切る。** 全呼び出しで JSON が崩れず、引用の合格率も高い（人間の考えの引用は、sora6（30区間）で74件中73件、sora7（14区間）で45件中45件が合格。sora8（14区間）で、A の全見出しの引用は133件中129件が合格）。指示文の調整で出力が大きく動くのは、見出しの定義と決定語まわりが主で、それは定義の確定で済んだ。
- **B は、上限に関わらず件数をほぼ埋める。** 数え方は、塊ごとの B の件数。sora6 は30区間（41塊）、sora7〜sora9 は14区間（19塊）を対象にした。
  - sora6（上限3、30区間・41塊）：3件が39塊、2件が1塊、1件が1塊。そのうち14区間と重なる9区間（10塊）と、同じ6区間（6塊）は、どちらもすべて3件。
  - sora7（上限5）：19塊すべて5件（同じ6区間の6塊も5件）。
  - sora8（上限3）：19塊すべて3件（同じ6区間の6塊も3件）。
  - sora9（種別を足した。上限3）：捨てる前は19塊すべて3件（同じ6区間の6塊も3件）。
  - 「なければ空でよい」「件数を合わせるために書かない」の指示は、件数に効かない。
- **種別は自己申告で、裏づけがない。** sora9 の14区間（57件）：推奨10 / 判断20 / 設計方針19 / 作業報告8 / 従順0。引用に合図語（おすすめ・推奨・妥当・が良い・べき・不要・してください など）がある項目は、全体で57件中3件（5.3%）。推奨と分類された10件の引用には、合図語が0件。判断は20件中3件。
- **逃げ道を混ぜた選択式の設計は、失敗した。** 種別に作業報告と「人間の指示への従順」を混ぜて、機械で捨てる設計は、従順が0件で使われず、作業報告も8件（14%）にとどまった。捨てたあとの残りは、13塊が3件、4塊が2件、2塊が1件。
- **分類が安定しない例：** ある座（773）で、sora7 にあった項目のうち、推奨にあたると見ていた2件は、sora9 では判断に分類された。判断にあたると見ていた1件は、sora9 の出力に出てこなかった（件数の枠が別の項目で埋まった）。項目の内容は書かない。
- **誤読（本文と引用の意味ずれ）は、機械で検出できない。** B の引用の合格（sora8：57件中56件、sora9 の残り49件中42件）は、引用が入力にあることしか示さない。
- 本文と引用がほぼ同一（Dice 0.9以上）の B の項目は、「言い換えるだけ」の指示で減った（14区間で18件 → 1件）。A では減らない（90項目）。
- **所要時間の実測（sora9、14区間・19塊）：1塊あたり、A約44.7秒、B約61.2秒**（計約105.8秒）。1塊あたりの計は、sora7が112.5秒、sora8が100.7秒（どちらも同じ14区間）。sora6は30区間（41塊）で89.0秒で、14区間と重なる10塊だけでは85.2秒。この14区間は層別の標本ではなく、長い座が混じる。
- 候補モデルの読み比べ（`qwen38-27b-q2k-waka`、`qwen3:30b-a3b`）は、途中で打ち切った（27b は一部、30b は未実施）。試走はすべて `qwen3-14b-16k`。

### 決定：第1段階はAのみ

- B は第2段階に先送りする。第1段階は、A のみで全833座を生成する。
- 見込み：942塊 × A約44.7秒 ≒ 42,100秒、約11.7時間。ただし、層別の標本ではない（1塊あたりの秒数は、長い座が混じる14区間での実測）。最初の100座の実測で見直す。
- 決定項目のリンクは、機械的に付ける（LLM は使わない）。決定の引用を、人間の発言と機械照合して発言を特定し、その発言の直前の assistant メッセージを結ぶ。
  - 直前の assistant メッセージは、**候補**として結ぶ。断定しない。直前の発言が、決定の対象とした提案とは限らないため。`diary_links` に `link_kind` の列を持たせ、候補であること（例：`preceding_assistant_candidate`）を区別して記録する。人間の発言そのもの（根拠）へのリンクとは、`link_kind` で分ける。
  - 引用が、座の中の複数の人間の発言に一致するときは、**座の中で時刻（`occurred_at`）が最も早いもの**を採る。同時刻なら `message_id` が小さい方。決定的に1つに決まるようにするための規則で、正しい発言とは限らない。
  - 一致する発言がないときは、リンクを付けない。
- 機械後処理（重複除去、塊の連結、再分類ルール（c））は、第1段階に含める。

### 第2段階の方式案（Bの再設計。案・未検証）

試走で B の件数の埋め込みと、種別の自己申告の問題が出たので、方式を変える。モデルの変更も含めて再検討する。考え方の根拠は、mizchi/jev-playground の知見とされるもの（逃げ道は別の noul にする、順序のある判断は score にする、境界帯は人に回す）。参照先の内容は、こちらでは確認していない（依頼者から提供された説明による）。

- Claude の発言を、1件ずつ独立に判定する。件数の上限は設けない（上限が件数を埋める原因なので）。
- 「種別」の選択式（逃げ道を混ぜた choice）は使わない。
- 独立した○×の質問（noul）の束にする。①人間に選択を促す提案を含むか ②評価・承認・却下を含むか ③完了作業の報告のみか。
- 閾値は質問ごとに引く。境界帯は「保留」とし、機械的に採否を決めない（人に回す）。
- 軽量モデル（`qwen2.5:1.5b` 級）での代用を、第一候補として試す。
- 候補は、決定項目の直前の発言と、合図語を含む発言に絞る。
- 採否は、人手の正解（約30件）で決める。一致率ではなく、乖離したケースの内容を読んで判断する。
- `diary_entries` に `model`、`prompt_version`、`rule_version` を持たせ、B を別のモデルで作り直しても、A の結果を壊さないようにする。

#### 判定モデルの代用と、判定の層（Jev の代用）

- Jev は、TypeSafe社のものとされる判定専用のモデルで、生成はせず、分類・スコア・ルーティングだけを行うとされる（いずれも依頼者から提供された説明で、こちらでは確認していない）。手元で動かす手段が確認できていないため、当面は軽量の汎用LLM（`qwen2.5:1.5b` 級）で代用する。
- 代用するときの条件：
  - 出力は「はい／いいえ」または 0〜1 の数値だけ。Ollama の `format` で、列挙型（はい／いいえ）か数値のスキーマに固定する。文章でラベルを付けさせない。
  - `logprobs` が使えるかを、試走で確かめる。使えるなら、確率をスコアとして使う。使えない場合の扱い（数値スキーマの出力で代える、など）は、試走の結果を見て決める。
  - 判定は1件ずつ独立に行う。件数の枠を持たせない（上限が件数を埋める原因なので）。
- 判定の呼び出しは、1つの層にまとめる。質問の型は choice / score / noul の3つ。Jev 本体を手元で動かせることが確認できたときに、同じ質問の型のまま、判定の層だけを差し替えられるようにする。質問の中身（上の①〜③）と閾値は、層の外（設定）に置く。
- 状況：案。判定の層、`logprobs` の確認、質問と閾値の設定は、未着手。

### モデル

- 呼び出しはRubyLLMの `RubyLLM.chat` を直接使う（`acts_as_chat` などのRails連携は使わない。既定のテーブルが、追記専用の `messages` と衝突するため）。

### タグ

### バックアップ（実装済み）

- `bin/backup-db`：`pg_dump` を gzip し、検証（`gzip -t`）してから配る。`.partial` で書いて、名前を直す。
- 保存先：外付けHDD（必須。書けなければERROR）と、外付けSSD（マウントされていれば）。それぞれ7世代を残す。

- ログ：`log/backup.log`。復元は別名DBに戻して件数を確認する手順を確認済み。
